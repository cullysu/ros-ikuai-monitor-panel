## Operator decision

Within five seconds, an operator must determine evidence freshness, service usability, the highest-risk affected object, and the next investigation workspace without mistaking missing or historical data for current evidence.

## Accepted product decisions

- Engineering release, product acceptance, design acceptance, and user acceptance are separate gates.
- Proof, Signal, and Object must answer different questions rather than repeat copy.
- Fleet scale is secondary whenever a concrete incident exists.
- “Action” language is reserved for controls carrying object, evidence-time, and return context; fixed-route links are “continue investigation”.
- Every public route receives a maturity label: `complete`, `bounded-readonly`, `fallback`, or `unavailable`.
- A route count is navigation coverage, not a count of mature modules.
- Mobile and desktop may use separate render trees, but must share typed domain semantics, inspector vocabulary, evidence rules, and visual tokens.
- Product completion requires independent acceptance and real RouterOS duration evidence; implementer review cannot self-close it.
- Accessibility evidence is a user outcome: the four primary routes must reflow at 200% and 320 CSS px, expose named controls, and support a complete keyboard object journey. DOM markers or a single Overview screenshot cannot close the gate.
- A short mobile object list is not complete when existing object evidence is hidden behind an avoidable second tap. When viewport capacity permits, a semantically justified preview may bring new domain evidence forward without writing selection state, guessing an object, or repeating aggregate counts.
- Dense viewport capacity does not create evidence priority. When no attention, verified path, active default route or timestamped latest-log candidate exists, a dense collection remains a list until the operator selects an object; row position, sort order and pagination are never preview reasons.

## PDR-196 — Single-thread incident patrol and capacity-aware tablet investigation

- status: `selected-before-red`
- validForCommit: `local unpublished remediation after a414f7ae`
- supersededBy: `null`

### Operator job

During a phone incident patrol, the operator must understand one dominant judgment within five seconds: what is failing, which concrete object is responsible, why it outranks concurrent risks, and which next evidence is worth opening. On a tablet, the operator must compare affected objects and inspect one object without the second pane becoming empty or inventing a selection.

### Information ownership

- **Proof** answers only “may I use this snapshot?”: evidence mode, age, source/boundary. It owns no resource or WAN diagnosis.
- **Primary risk** answers “what requires attention first and what is its impact?” It owns the concrete object, impact and one concise reason.
- **Related risks** answer “what else is concurrently wrong?” They are compact queue rows, not second hero sections.
- **Signal** answers “how is the primary risk changing?” A chart appears only when it explains the primary risk or after explicit expansion. WAN trend cannot dominate an interface/resource incident merely because rates are available.
- **Object evidence** answers “what new facts prove or bound this object?” It must add threshold, dependency, continuity, event/source or related-object comparison rather than restating the primary row.

### Three materially different directions

#### A. Incident document

One long narrative block contains verdict, primary object, evidence and next action; all related risks are appended below. It creates a strong editorial hierarchy on a phone, but it remains document-like, makes comparison slow and repeats the same object when the user drills in. Rejected.

#### B. Dense comparison board

Phone and tablet both start with a compact multi-object matrix: objects in rows, current/threshold/impact in columns, optional sparklines. It maximizes scan density and resembles a network appliance, but the 320–390px phone cannot preserve readable labels, 44px targets and multiple evidence columns without horizontal compromise. Rejected for phone; its comparison grammar is retained for tablet.

#### C. Focus queue + investigation workspace — selected

Phone renders a compact proof strip, one primary-risk focus row, a collapsed related-risk queue, then one context-sensitive signal/evidence region. The selected object opens a full-screen evidence destination. Tablet renders a persistent risk/object queue on the left and an investigation workspace on the right; without explicit object selection, the right side shows a collection comparison and shared dependency/source context, never a fake selected detail. The primary risk receives the only strong tonal emphasis. Related risks use neutral rows with explicit severity words and counts. Charts use space only when they answer the active question. No new card grid, side stripe, giant verdict panel, decorative gradient, tiny text or fake grabber is permitted.
