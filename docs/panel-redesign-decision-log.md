## 总目标

把当前只有 Overview 外壳的演示页重做成可以公开使用的 RouterOS 只读监控产品。完成标准不是“首页截图好看”或“现有检查全绿”，而是：

1. 正式导航都能进入真实模块，并支持深链、刷新、Back / Forward；
2. 首次连接、连接测试、错误恢复和设备切换真实可用；
3. 快照有轮询、可见性恢复、手动刷新、请求失败与过期降级；`navigator.onLine` 只作提示，不能阻断 LAN 内同源请求；
4. 手机是独立任务架构，不是桌面事故报告缩窄；
5. 图表是有时间、单位、比例尺和空态的响应式 SVG；
6. HTTPS / SSH 指纹、会话、安全头和 API Schema 形成明确安全边界；
7. CI 覆盖全部路由、状态、交互、可访问性和安全要求；
8. 上传 GitHub 后，精确 SHA 的 Linux、Windows、GHCR CL 全部通过。

## 步骤 3：复核首次登录与连接能力

### 已观察事实

- 后端实际上已有：`GET/POST /api/router-login`、保存登录资料、注销和忘记资料接口。
- 后端会分别测试 SSH 与 REST，并返回通道结果和警告。
- 前端没有真实登录/连接 UI，因此 README 所述首次进入流程无法发生。
- 发布检查曾以不存在的兼容字符串代替真实表单验证。

### 判断

这一项应优先复用现有后端能力，而不是重新发明认证协议；但必须先修复传输风险和前端运行时契约。

### 为什么这样做

最小且正确的垂直切片是：启动状态查询 → 未配置时显示连接页 → 输入凭据 → 连接测试 → 成功进入面板 → 失败显示真实通道错误 → 可切换设备或注销。

### 风险

- 当前 RouterOS REST 使用 HTTP Basic；
- SSH 使用未知主机自动信任；
- 保存资料虽然不持久化密码，但 UI 文案和行为仍需准确说明；
- CSRF 与本地会话流程必须由真实浏览器测试覆盖。

### 心得

后端“已经有接口”不等于产品“已经有功能”。用户任务只有在前端、后端、错误恢复和文档共同闭环时才成立。

## 步骤 4：复核快照生命周期

### 已观察事实

- `src/panel-framework/main.tsx` 只请求一次 `/api/snapshot`。
- 请求失败被静默捕获，并回退到测试用 `no-snapshot` fixture。
- 页面没有轮询、手动刷新、可见性恢复或网络离线处理。

### 判断

必须删除生产运行时 fixture 回退。测试 fixture 只能通过明确测试注入进入应用；真实 API 失败必须成为可恢复的错误状态。

### 为什么这样做

监控产品最危险的错误不是页面崩溃，而是旧数据继续以“当前”口吻显示。数据年龄必须驱动视觉和语义降级，而不是只在首次渲染时计算一次。

### 计划中的状态机

- `idle`：尚未请求；
- `loading`：首次加载；
- `current`：数据在允许年龄内；
- `refreshing`：保留当前视图并刷新；
- `stale`：超过年龄阈值；
- `offline`：浏览器离线；
- `error`：请求失败且无可用快照；
- `recovering`：失败后重试；
- `unauthorized/unconfigured`：需要连接 RouterOS。

### 心得

“当前证据”是随时间变化的状态，不是快照载入那一刻写死的标签。

## 步骤 5：确定实施顺序

### 决策

实施顺序固定为：

1. 真实路由和正式模块；
2. 连接/登录与运行时 Schema；
3. 快照轮询、恢复和年龄降级；
4. 手机任务架构及首屏重做；
5. SVG 图表；
6. 后端安全边界与模块拆分；
7. 全路由 CI 和发布。

### 为什么不是先改颜色和字号

当前最大问题是产品行为不成立。先做视觉会迫使后续真实导航、错误状态和连接流程迁就一个错误的信息架构，再次产生 CSS 补丁层。

### 产品方向

- 手机：`概览 / 接口 / 终端 / 日志 / 更多`，异常优先但不重复计数；
- 桌面：控制台式主导航与对象工作区；
- 共用数据语义与路由清单；
- 手机与桌面保持独立渲染树和样式入口；
- iOS 纪律用于触控、层级、安全区和过渡；
- iKuai 性格用于紧凑对象信息、冷蓝灰阶和精确状态。

### 心得

优秀的移动端不是把信息删少，也不是把字号缩小；它是在有限首屏里提高“每次扫视能做出的正确判断”。

## 步骤 7：建立真实 React 路由，但不把数据展示壳冒充完成模块

> **后续纠正**：这一阶段只证明 URL、内容切换、焦点和历史行为已经真实成立。旧壳层的无效 `#dns`、搜索和只读按钮当时尚未全部收回；“正式模块”一词表述过头。

### 已观察事实

- 旧版侧栏点击只切换 `.is-active`，URL、主内容、焦点和浏览器历史没有同步变化。
- 18 个既有入口都需要保留稳定深链，但手机一级导航不能同时承载 18 个标签。
- 后端快照已有接口、WAN、路由、终端、DHCP、ARP、连接、DNS、安全、资源和日志字段，可以先建立真实只读模块，不需要用演示数据填充页面。

### 判断与取舍

- 建立一个类型化路由注册表，作为桌面侧栏、手机任务导航、URL 解析、标题和验收的共同事实来源。
- 采用“18 个正式路由 + 5 个手机任务组”，而不是复制 18 个手机 Tab。
- 缺失数据渲染为空态或不可用，不用 mock、fixture 或零值填充。
- Overview 与其他 URL 按路由选择真实 React 页面；这一阶段仍只是数据展示壳，只有补齐搜索、筛选、排序、分页、对象详情和错误态后才能称为完成模块。

### 为什么这样做

真实导航必须同时改变 URL、页面内容、文档标题、焦点和 Back / Forward 历史。只让按钮变蓝会让用户误以为已经进入模块，也会让自动验收产生假通过。先建立稳定路由所有权，后续登录、轮询、图表和移动信息架构才有可靠挂载点。

## 步骤 8：建立真实连接、Schema 与快照生命周期

### 判断与取舍

- 最近可用快照可以在刷新故障时保留，但必须改为历史/恢复/离线边界，并隐藏当前速率声明。

### 未解决风险

- RouterOS REST 仍使用 HTTP，SSH 仍自动信任未知主机；公开发布继续禁止。

- 连接页面完成的是功能垂直切片，不代表被拒绝的手机 Overview 已经合格。

### 心得

- 错误优先级也是证据语义：一个旧的通道警告如果遮住当前 Schema 失败，会让用户错判真正阻断点。

- 视觉复核必须发生在 DOM 检查之后。真实按钮落在首屏之外，是自动语义检查很容易漏掉的任务失败。

## 步骤 10：用三案评审与官方规范确定新手机 Overview

### 已观察事实

- 三个互不依赖的设计方向已经完成：单滚动运维账本、巡检队列与对象钻取、实时网络仪表。
- 三案一致反对旧版的大型深色结论块、事实复读、横向对象轮播、假面板交互和 768px 空洞侧栏。
- Apple 的布局、字体、Tab Bar、披露控件和图表规范都强调阅读顺序、可预测交互、可读文字、渐进披露与有明确用途的数据图形。
- iKuai 与 UniFi 的公开产品资料共同说明：网络产品的专业感来自对象化状态、紧凑比较、风险与证据，而不是大卡片和装饰图形。
- 当前 live 页面存在两套设备/鲜度抬头；它们必须合并，而不是继续在 Overview 内重复。

### 备选方案

1. **单滚动运维账本**：判断最快、最稳，但正常态容易退化为静态规格表。
2. **巡检队列与对象钻取**：事故效率最高，但固定双栏可能重新制造平板空白。
3. **实时网络仪表**：正常态监控价值最好，但若所有异常都保留图表会压住事故对象。

### 决策与原因

采用“自适应运维仪表”：以账本作为永久骨架，以纵向 Top 3 队列承载异常，以一张真实 SVG WAN 趋势承载正常态。

- 正常态：结论、证据、三个事实后显示趋势；不制造空的告警列表。
- 异常态：Top 3 对象取代图表的首屏位置；图表下移或在证据不相关时删除。
- 图表只有在至少两个带时间戳的当前样本存在时显示；一条样本不伪装成趋势，历史或不可用证据不画当前图。
- 768px 保持独立手机树，但不固定空洞双栏；只有两侧都有信息价值时才并排。
- 900px 起由桌面工作区负责连续重排，禁止缩小文字或退回手机树掩盖 1024/1180 问题。

### 验收定义

- 390×844 异常首屏同时看见刷新、业务证据、结论、三个不重复事实和最多三个受影响对象。
- 320/360/390/430/768/1024/1180 与七类场景均有截图和结构检查。
- 正文/数值不低于 16px，元数据不低于 13px，触控目标不低于 44px。
- live 页面不得出现重复设备身份或重复鲜度条。
- Back/Forward、焦点恢复、200% 文本缩放、ARIA 关系和 reduced motion 必须通过。

### 心得

“iOS 风格”不是毛玻璃数量，“爱快风格”也不是蓝色表格数量。真正可复用的共同点是：稳定导航、明确对象、克制层级、可验证证据和快速进入下一步。图表必须有任务，空白也必须有理由；否则都只是美术占位。

### 下一步

先写新模型契约和场景级失败测试，再删除旧手机组合组件与样式，重建 Overview；运行时状态机和真实路由必须始终保持绿色。

## 第 11 步：让新手机界面、验收门禁和异常节奏说同一种语言

**日期：** 2026-07-16
**状态：** 实现与聚焦验收完成；全尺寸最终矩阵仍待运行

### 这一轮发现了什么

1. 产品代码已经删除旧 `mobile-native` 页面，但三套静态/架构门禁和 CSS 格式器仍读取旧文件。若为让脚本通过而恢复旧文件，就会把已经否决的设计重新带回产品。
2. 接口异常的 `compactVerdict` 一度显示失败。截图中的结论区实际只有约 122px；真实原因是测试完成 Back/Forward 后继续使用已经卸载的旧 DOM 节点，测得高度为 0。
3. Fleet 测试数据本身包含 3 个未运行接口。旧预期仍要求显示“网络可用”，这会让规模属性压过真实事故，正好重犯评审指出的问题。
4. 资源满载页继续显示 WAN 图，会让次要流量证据抢占资源事故的空间；CPU、内存、磁盘的真实值也不够直接。
5. 折叠的证据来源使 390px 正常页和 768px 平板留下大块空白，信息虽正确，但巡检效率不够。

### 考虑过的方案

- **恢复旧文件或放宽旧门禁：拒绝。** 只能制造“脚本绿了、产品倒退”的假通过。
- **删除相关门禁：拒绝。** 会失去对证据语义、旧组件复活和伪交互的阻断。
- **把门禁迁移为新产品契约：采用。** 检查三项核心事实、真实 Top3 对象及路由归属、当前证据图表、旧树彻底删除、触控/字号/ARIA/响应式和矩阵完整性。
- **用更大高度阈值掩盖 0px：拒绝。** 先修复测试使用失效 DOM 的时序，再保留原来的紧凑度要求。
- **资源事故保留 WAN 图：拒绝。** 正常页才显示 WAN 当前趋势；任何事故页先服务当前事故。
- **用更多重复卡片填空：拒绝。** 改为默认展开“证据来源”，所展示的是目标、成功时间、失败记录和只读边界，不重复三项判断事实或事故对象。

### 实施决定及理由

1. 将 `check-overview-architecture.js`、`check-overview-ikuai-static.js`、`check-public-release-readiness.js` 和 CSS 格式器全部迁移到 `mobile-overview` 新目录。
   - 理由：门禁必须约束当前产品，而不是约束已删除的历史产品。
2. 门禁明确禁止旧 `mobile-native` 文件和 `.mn-*` / `data-mobile-native*` 命名复活。
   - 理由：用户要求手机端与旧实现彻底隔绝，这应成为可自动验证的架构事实。
3. 浏览器交互完成后重新查询当前路由的 DOM，再进行几何检查。
   - 理由：React 路由切换会卸载旧节点；失效节点的 0px 不能代表视觉失败。
4. 路由焦点测试从固定等待 60ms 改为在 1.8 秒上限内等待“路由已稳定且标题已获得焦点”。
   - 理由：验证的是可观察结果，不应依赖机器偶然的单帧时序；没有在产品代码中加入轮询补丁。
5. Fleet 的验收预期改为“真实接口事故优先”，不再把 fleet 当作健康状态。
   - 理由：规模是属性，不是风险；最高风险必须决定结论、事实和默认对象。
6. 资源事故的三项事实改为 CPU 96%、内存 92%、磁盘 97%，每项带阈值；事故对象只补充“3 项超阈值、尾部连续 6/6 个采样点”。
   - 理由：事实层回答“当前值是多少”，对象层回答“哪个对象、持续多久”，避免复读。
7. WAN SVG 只在 `current + risk=none` 时显示。资源、接口、全离线、采集异常和无快照都不显示正常态流量图。
   - 理由：异常布局必须真正改变权重，而不是只换标题或颜色。
8. 证据来源默认展开，仍可由用户收起。
   - 理由：用新的来源与边界信息填充手机和平板工作区，而不是用重复指标或装饰占位。
9. 将次要文字色从 `#607985` 加深为 `#536e79`。
   - 理由：它在三种浅色表面上的最低对比度由不足 4.5 提升到约 4.69。

## 第 12 步：桌面端不再修旧报表，重建为“冷蓝运维账本”

**日期：2026-07-16**
**产品循环阶段：设计 → 架构 → 实现 → 首轮视觉验收**

### 1. 这一步解决的不是“换皮”

复核旧版 1024×768 和 1180×820 截图后，确认旧桌面概览存在四个根本问题：

1. 7–10px 小字和大量细表格把阅读成本转嫁给用户；
2. CSS 尺子和盒模型线条冒充趋势图，没有真实时间序列；
3. 正常态主列过长，右侧下半屏却空着，空间分配失衡；
4. `StatusVerdict → DesktopWorkspace → DesktopDecisionRail → scene builder → 多层 CSS override` 的所有权过碎，继续改只会产生新补丁。

所以本阶段的目标不是保留旧 DOM 后调字号，而是删除旧活动渲染树和旧样式所有权，建立一个可以解释每一项数据来源的新桌面产品。

### 2. 比较过的三种方向

#### A. Operations Ledger（运维账本）

- 状态总线只回答结论、证据、默认路由、采集；
- 主工作区用一张真实 WAN 图和对齐账本；
- 事故态用对象清单替换正常图表。

优点：最符合爱快式快速扫读；在 1024 宽度也能成立；模块所有权最清晰。
风险：如果对象路径太弱，可能退化成普通报表。

#### B. Evidence Workbench（证据工作台）

- 以设备、接口、默认路由、下一跳的所有权链为中心。

优点：因果关系最强。
放弃原因：现有快照并不总能证明完整关系；为了视觉完整去补关系，会重犯“拓扑伪造”的错误。

#### C. Patrol Queue Command Console（巡检队列）

- 事故对象队列优先，正常对象折叠。

优点：事故扫描速度最快。
放弃纯 C 方案的原因：深色指挥中心会和手机端浅冷蓝产品分裂，正常态也缺少稳定的数据工作台。

### 3. 最终选择

选择 **Cold-blue Operations Ledger（冷蓝运维账本）**：

- 以 A 作为永久结构；
- 用 C 的事故优先级决定异常布局；
- 只采用 B 中能被快照明确证明的来源路径；
- 手机、桌面只共享 `current / historical / unavailable` 证据模型，不共享组件或 CSS。

这不是折中配色，而是明确的信息架构选择：**一个数据只有一个主要位置；顶层只做交叉引用；异常必须替换布局，不只是换颜色。**

### 4. 实际实现与删除

新增独立桌面树：

- `DesktopOverviewScreen.tsx`
- `DesktopWanEvidence.tsx`
- `DesktopIncidentDocket.tsx`
- `DesktopLedger.tsx`
- `desktopOverviewModel.ts`
- 三个独立桌面样式文件（tokens / component / responsive）

共享证据模型迁移到：

- `overview/evidence-model/buildOverviewEvidenceModel.ts`
- `overview/evidence-model/overviewEvidenceTypes.ts`

明确删除：

- 旧 `DesktopConsole / DesktopDecisionRail / StatusVerdict`；
- 旧 scene builder、伪图表、资源行、WAN 行等 20 个桌面 TypeScript 文件；
- 旧 `overview-desktop / overview-states / desktop/refinement` 等 21 个活动 CSS 文件；
- 旧 CSS 不再只是“不 import”，而是从源码删除。

构建结果由旧阶段约 **222KB CSS** 降到 **50.35KB CSS**；JS 约 **443.87KB**。缩减来自删除旧活动架构，不是压缩掉功能。

### 5. 数据真实性约束

1. 默认路由只接受 `active=true && disabled!==true`；没有记录就显示“无法核实”，禁止首行兜底。
2. 缺失速率保持缺失，不转成 `0 bps`。
3. 正常单设备、当前证据且历史尾点与当前值一致时，才绘制 WAN SVG。
4. Fleet 不绘制虚构的“平均趋势”；真实接口风险优先于 Fleet 规模。
5. `all-offline / no-snapshot / collection-down / resource-full / interfaces-down` 均结构性移除 WAN 图。
6. 资源事故只声明 CPU、内存、磁盘、阈值和尾部连续样本，不由资源值推断网络已经中断。
7. 管理面、转发面、业务面分别陈述，REST/SSH 可达不冒充业务可用。

### 6. 图表为什么这样做

正常态使用响应式 SVG，而不是 CSS 盒模型：

- 固定 `viewBox`，容器改变时比例不变；
- 下载、上传两条真实时间序列；
- 明确单位 `bit/s`；
- 显示当前下载、当前上传、窗口峰值、采样点和时间窗；
- `<title>` 与 `<desc>` 提供无障碍摘要；
- 没有真实阈值时不画阈值线；
- 事故、历史、不可用场景不画“看起来还活着”的曲线。

### 7. 首轮失败与修正

首轮截图暴露了一个真实问题：1024px 视口扣除 176px 侧栏后，右侧账本只有约 326px。旧式五列表格虽然没有触发页面横向滚动，却被容器 `overflow:hidden` 裁掉；这类“overflowX=0”不能算成功。

修正：

- 900–1039px 主工作区右栏改成两列证据行；
- 状态、对象、证据、来源逐行换行，不截断关键文本；
- WAN 峰值不再用省略号；
- 账本详情按钮补足 28px 桌面点击高度；
- 运行门禁直接检查可见文本是否被裁剪，而不是只检查页面是否横向滚动。

另外发现旧验收仍要求已经删除的 `DesktopWorkspace / StatusVerdict / incident.css`。没有为了让旧测试变绿而恢复旧代码，而是：

### 5. 打开路由不代表数据语义正确

对业务分区模型做单独契约检查时，发现数个容易被普通 smoke test 漏掉的问题：

1. `Number(null)` 会得到 `0`，可能把“没有采集到”改写成“测得为零”；
2. `value || "—"` 会把合法的显式零值当成缺失；
3. 不完整的 WAN 上下行数据可能被聚合为看似完整的速率；
4. 缺失的连接总数、活动线路、资源值和 DNS 运行状态，可能被显示成确定结论；
5. 历史快照页面虽然标题提示过期，表格中的数字仍可能保持当前态语气；
6. 不可用状态如果只隐藏标题数字、却保留业务表格，用户仍会把旧数字当成当前状态。

这些问题没有 P0 的任意路由兜底严重，但都会侵蚀监控产品最重要的可信度。

### 6. 采用的修正原则

这一轮统一采用以下语义规则：

- `null / undefined / 空字符串` 保持缺失，不转换为零；
- 明确观测到的数值 `0` 仍然正常显示；
- WAN 任一方向缺失时，不显示伪完整的聚合上下行；
- 接口运行数只统计明确的 `running === true`；
- 缺失连接总数、活动线路、资源值、DNS 状态均显示“未记录”或缺失态；
- 历史证据把当前标签全部改为历史语气，并明确数字不代表当前状态；
- 不可用证据隐藏业务数字和表格，只保留失败边界、明确的上次成功时间和“对象无法判断”；
- `defaultRoutes` 集合本身可作为默认路由记录来源，但不能因此推断活动路径；
- 表格渲染不得再用会吞掉显式零值的 `||` 兜底。

## 第 14 步：把“只读”从文案延伸到传输、身份和会话

### 1. 这一阶段解决的不是配色，而是证据链入口

前端即使严格区分当前、历史和不可用，如果连接层会静默使用明文 HTTP、自动接受未知 SSH 密钥，或者任意 GET 都能无限创建会话，那么页面上的“当前证据”仍缺少可信入口。因此先按官方资料核对了三类要求：

- MikroTik REST：推荐通过 `www-ssl` 使用 HTTPS；普通 `www` 上的 Basic 凭据可能被被动读取；
- Paramiko：未知主机密钥默认应拒绝，不能使用 `AutoAddPolicy` 自动信任；
- 浏览器响应边界：CSP、`frame-ancestors 'none'`、`nosniff`、Referrer Policy 等必须由真实后端响应提供，而不是只写在文档里。

### 2. 采用的最小安全方案

新增两个后端模块：

- `panel_backend/router_transport.py`：拥有 REST 协议、端口、TLS 校验、URL 构造、SSH SHA-256 指纹和固定密钥策略；
- `panel_backend/session_security.py`：拥有有界 TTL 会话存储和滑动窗口限流。

具体行为改为：

1. RouterOS REST 默认 `HTTPS + 443 + 证书校验`；
2. HTTP 或关闭证书校验都必须显式确认风险，不能自动降级；
3. 地址栏只接受 IP 或主机名，输入带 `https://` 的 URL 会直接报错，避免协议被悄悄吞掉；
4. 第一次 SSH 连接在发送密码前停下，显示算法与 SHA-256 指纹；
5. 用户核对并确认后固定该指纹，后续指纹变化直接阻断；
6. 保存设备资料只保存地址、端口、REST 设置和 SSH 指纹，永不保存密码；
7. 任意静态 GET 不再创建会话，只有明确的连接/网络设置启动路径可以初始化；
8. 会话有 TTL、总量上限和登录/初始化速率限制，`429` 返回 `Retry-After`；
9. 后端统一发送 CSP、DENY 嵌入、`nosniff`、`no-referrer`、Permissions Policy 和 same-origin 资源策略；
10. `Server` 头不再泄露 Python 版本。

### 3. 连接界面为什么也必须改

连接页增加 HTTPS/HTTP 分段控件、REST 端口、证书校验开关、显式风险确认和 SSH 指纹确认区。这里没有把风险藏进“高级设置”，因为用户作出的不是审美偏好，而是凭据是否可能明文暴露、设备身份是否被验证的安全决定。

`_acceptance/panel-runtime-browser/mobile-ssh-host-key-confirmation.png`

已同步更新 Docker、本地、Windows EXE、RouterOS Container、README、安全策略、凭据说明和威胁模型。所有当前文档统一为：

- RouterOS REST 默认使用 `www-ssl`；
- 不会静默回退 HTTP；
- 首次 SSH 必须核对并固定指纹；
- 保存资料不保存密码；

### 6. 本步心得

1. **HTTPS 默认值不够，静默解释同样危险。** 如果地址栏接受完整 URL 后只取 hostname，用户会误以为其协议选择被保留；因此必须拒绝含协议的输入。
2. **SSH 指纹确认必须发生在密码之前。** 先认证、后提示指纹并不能建立可信身份链。
3. **保存资料和保存密码是两件事。** 地址、端口和固定指纹有长期价值，密码没有必要进入本地历史文件。
4. **“本机页面”仍需要会话上限。** localhost 不是无限资源许可，任意 GET 创建会话会被浏览器预取或探针放大。
5. **响应头必须通过真实 Handler 验证。** 模拟服务器能测 React 流程，但不能证明生产 CSP 没有把真实资产拦坏。

## Step 16｜把安全输入与采集执行从 `app.py` 拆成可验证边界

### 这一步要解决什么

手机和桌面表面已经有了独立渲染树，但后端仍把保存资料、API 输入解释、RouterOS REST/SSH 执行和快照组装放在同一个大文件中。继续在 `app.py` 内追加判断，会让安全规则只能依赖人工记忆，也会让后续修改采集策略时误伤 HTTP 边界。

这一步不追求一次性搬空 `app.py`，而是先抽出最容易定义不变量、也最值得直接测试的四条边界：

1. RouterOS 连接资料只能保存元数据和 SSH 指纹，永远不能保存密码；
2. API 请求体必须先通过对象型 JSON 契约，才能进入业务逻辑；
3. Collector 不再自行实现 REST/SSH 请求、重定向处理和流捕获；
4. 连接跟踪与 DNS 行的解释必须是纯解析，不和采集线程、会话或 UI 绑定。

### 为什么这样拆

- **先拆有安全不变量的深模块，而不是按文件行数平均切块。** `RouterProfileStore` 同时拥有规范化、迁移、原子写入、去重、历史上限和公开投影，调用者只看到“记住/查找/删除”，无法顺手把密码重新塞回 JSON。
- **API Schema 必须在 Handler 最前面阻断错误形状。** 旧行为会让数组或 `null` 进入 `payload.get(...)`，最后变成 500。现在乱码、非 JSON、非对象 JSON 都稳定返回 400，错误不再穿透到 RouterOS 登录逻辑。
- **采集器负责“采什么、怎样组成证据”，传输器负责“怎样安全执行”。** `RouterCollectorTransport` 统一拒绝 REST 重定向、执行可选端点降级、汇总必需端点失败、处理 SSH 命令与有界流捕获。Collector 中只保留短委托方法，避免两套安全语义再次分叉。
- **解析器必须纯净。** `ConnectionEvidenceParser` 处理连接统计、terse 行、IPv4/IPv6 端点、去重、速率单位和 DNS 行展开。这样缺失、重复和地址格式的语义可以直接测试，不需要启动采集线程。

### 实际改动

## 第 24 步：接受合并评审，撤销过度结论并回到设计/架构阶段

### 已观察事实

1. 生产后端原有时间函数没有形成端到端 RFC 3339 契约；修复测试时区并不能替代修复生产协议。
2. `navigator.onLine` 描述的是浏览器对互联网连接的判断，不代表本地面板、交换网络或 RouterOS 不可达。
3. 19 个 URL 能显示不同数据，不等于 19 个完成的运维模块；通用表格缺少对象操作能力。
4. 事故页面存在可用证据却仍留白，说明 proof、signal、object 三层职责和展开策略没有完成。
5. 三栏导航压缩了终端与日志这两个高频巡检任务；大型状态块又重新抢占首屏。
6. 768/844 只是把现有模块并排，未形成对象列表—详情检查器的平板任务架构。
7. 固定视窗与 DOM 检查没有证明 200% 文字重排；残留 Edge 锁也证明旧浏览器门禁不稳定。

### 决策与原因

- **时间**：后端统一 RFC 3339；前端先用严格正则确认带时区，再解析和格式化。原因是协议必须确定，显示时区才可以按用户本地化。
- **LAN 请求**：`navigator.onLine` 只进入辅助提示，不新增正式 offline 快照阶段，也不允许提前返回。原因是 WAN 断开时 LAN 仍可正常巡检。
- **手机主线**：正常态按“证据—结论—三个事实—当前 WAN—对象入口”组织；异常态用事故对象替换正常图表。原因是第一屏必须支持判断与行动，而不是复读规格。
- **导航**：稳定入口定为概览、网络、终端、日志，其余从顶部更多菜单进入。原因是四项分别对应四个高频任务，不能靠减少数量制造高级感。
- **状态区**：默认文字下目标约 64–76px；文字放大时允许自然增高。原因是压缩重复文案，不压缩可读字号。
- **平板**：600–1023px 使用侧任务栏、对象列表和详情检查器；1024px 才切换桌面树。原因是平板需要任务关系，而不只是机械两栏。
- **模块定义**：URL、数据壳、完成模块三层分开命名；完成模块至少具有真实错误态、搜索/筛选/排序/分页和对象详情中的适用项。
- **验收口径**：矩阵只证明工程覆盖；视觉与产品评审单独开门，任何一本账失败都禁止发布。

### 已实施的证据

- 新增后端 `panel_backend/time_contract.py`，生产 `format_iso_now()` 输出 RFC 3339 UTC；前端 `timeContract.ts` 与运行时 Schema 拒绝无时区时间。
- 快照请求不再由 `navigator.onLine` 短路；浏览器离线事件仍触发一次真实恢复请求，并只显示提示。
- 删除旧 `legacyBridge` 与公开 legacy 资源，`public/index.html` 只保留单一 React 根节点；同时不再声称旧壳已在历史版本中提前清空。
- 手机形成四个稳定入口；网络、终端、日志工作区具备搜索、筛选、排序、20 行分页、对象详情、Back/Forward 与焦点恢复。
- 事故中心按最高风险选择对象与目的路由；Fleet 只在无风险时作为规模属性。
- 证据台账按可用视窗、事故数量和证据数量自适应展开，不再固定折叠或固定展开。
- 手机/桌面 SVG 均保持宽高比并包含时间窗、单位、比例尺和可访问说明；没有时间戳的资源样本不再连成伪趋势。
- Playwright 门禁已有 120 秒全局看门狗、上下文回收和失败截图/HTML；真实 200% 浏览器文字调整测得 2.0 倍并检查裁切。
- 主机校验拒绝 `@`、`?`、`#`、路径、URL 和端口分隔符；损坏配置文件抛出明确错误并保留原文件；界面和 API 使用“记住连接配置”，不保存密码。

### 当前结论

上述实现仍处于本地未发布工作区。旧 SHA 的矩阵和三端 CL 只能证明旧提交的工程链，不能替代当前代码的产品、视觉、完整矩阵和精确 SHA 证据。公众发布继续禁止。

### 心得

1. 修正一条失败测试，不能自动证明其背后的生产协议正确。
2. 网络产品最危险的错误不是“页面少一个元素”，而是把互联网、LAN、管理面和业务面混成一个状态。
3. 高密度来自信息职责清楚和对象操作效率，不来自缩字号、堆 DOM 或把所有表面染成冷蓝。
4. 历史日志必须允许推翻自己；保留原判断但明确标注失效，比静默改写更可审计。

## 第 26 步：目标从未受阻，继续拆除不稳定桌面门禁

### 状态澄清

本轮开始时重新读取持久目标，状态为 `active`，从未调用“blocked”。界面出现“受阻”感，是因为旧桌面运行时检查在手写 CDP WebSocket 上超时，并不是整个目标停止。正确处理方式是把它当作一个局部失败继续诊断；只要仍有可做的安全工作，就不能停住，也不能把一次工具失败写成目标受阻。

### 旧 CDP 的根因与决策

旧 `check-resource-trend-balance.js` 自己分配调试端口、启动 Edge、轮询 JSON 端点、建立 WebSocket，再由三个包装器最多重试四次。它既可能留下浏览器锁，也会把第一次真实失败隐藏在“后来重试通过”之后。决定保留验收语义，但删除手写传输层：改用 Playwright `chromium.launch`、独立 context、页面异常收集、全页工件、120 秒全局超时和显式 context/browser/server 回收；三个包装器改为单次运行，失败立即暴露。

迁移后第一次并非通过，而是暴露了真实产品崩溃：当前 WAN 速率存在，但 history 没有带时间样本时，`DesktopWanEvidence` 仍读取 `last.down`。这说明“浏览器连通问题”修好以后，门禁终于看到了真正的空样本边界。产品改为显示“时间序列正在积累”，保留当前上下行读数，不画伪趋势；测试夹具使用 RFC 3339 `Z` 时间戳，并新增专门的 `desktopTrafficAccumulating` 用例，防止以后再次读空数组。

### 结果与心得

桌面正常趋势、趋势积累、无快照、全 WAN 离线和资源满载均在第一次 Playwright 运行通过；无 7–9px 文本、无裁切、无横向溢出、首屏状态和工作区均满足当前共享桌面契约。心得：重试不是稳定性，重试会掩盖稳定性；应先让单次失败可复现，再修传输层和产品边界。旧脚本约两千多行失效 DOM 规则被当前共享检查器替换，测试不再为已删除的页面结构守灵。

## 第 27 步：区分产品失败与本机 Python 启动失败

56 格手机矩阵第一次重跑在任何浏览器格子开始前就出现 `fetch failed`。报告的 serverExit 明确显示本机 `python` 命中了 uv trampoline，受当前沙箱限制无法创建 Python 子进程；显式指定真实解释器后又暴露缺少 `requests`，说明后端仍未启动。这不是手机产品失败，也不能靠重试或改门禁冒充通过。

决定让手机矩阵启动器优先解析真实 Python：显式 `CODEX_PYTHON_PATH/PYTHON`、项目 venv、用户 Codex bundled runtime，最后才回退系统命令；同时 `local-predeploy-check.js` 在存在 `_acceptance/python-deps` 时把它合并进 `PYTHONPATH`。这样本地不再依赖偶然 PATH，CI 仍使用 setup-python 的标准环境。修复后同一命令完成 7 场景 × 8 视口，56/56 与 56 张截图全部通过。

心得：门禁报告必须先回答“被测产品是否真的启动”。后端没启动时，矩阵覆盖为零是环境证据，不是视觉或业务结论；但环境问题也必须修到命令可复现，不能让操作者每次手工配变量。

## 第 30 步：时间契约不能只修测试，还要拒绝“看起来能解析”的错误日期

## 第 31 步：空壳快照不能被判成可运维证据

心得：Schema 的“对象存在”和运维的“证据存在”不是一回事；超时退出和可复现清理也不是一回事。

## 第 35 步：完整矩阵不能靠反复启动浏览器碰运气

56 格矩阵第一次在第 43 个格子启动 Edge 时中断，前后产品格子均通过。根因不是资源场景，而是 `local-predeploy-check.js` 在每个视口循环里重新启动一个浏览器进程；完整矩阵因此累计启动 56 次 Edge，把进程抖动误报成产品失败。

心得：场景隔离应使用 browser context，不应通过反复创建操作系统进程实现。稳定门禁的标准是单次可复现、失败归因准确、清理可证明。

## 第 36 步：语义门禁必须允许表面差异，但不能允许证据消失

心得：跨表面一致性是事实、层级和任务一致，不是复制同一句 DOM 文本；但“措辞不同”也不能成为空字段或错误对象身份的借口。

## 第 40 步：第一次远端失败是焦点时序竞态，不是停止理由

## 第 52 步：先统一未知、部分观测与默认路由的证据真值

### 为什么先做这一层

`19497d0` 评审中的前三个 P0 都属于事实合同错误，而不是视觉问题：缺失的 WAN/接口数组可能被解释成“观测到 0 个对象”，未提供的 `running` 可能被解释成在线，磁盘缺失可能掩盖已观测到的 CPU 99%，默认路由的标题、网关和活动状态还可能来自不同对象。监控产品一旦把“未知”写成“正常”，后续再漂亮的手机界面都会放大错误结论。因此本轮没有先改颜色或排版，而是先让移动、桌面与 RouterOS 视图消费同一份证据真值。

### 先建立失败用例

在 `tools/check-mobile-native-model.js` 中补充以下回归：

- WAN 数组缺失不得显示 `WAN 可用 0/0`；明确的空数组与缺失数组必须分开。
- `running === undefined` 不得计入在线或离线；接口对象缺失时不得显示“接口在线”。
- CPU 99% 已被观测时，即使内存或磁盘缺失，仍必须保留资源危险结论。
- 辅助 REST 通道错误或失败端点存在时，证据不得继续标记为当前且完整。
- 同时存在低距离非活动路由、高距离活动默认路由和活动非默认路由时，所有表面必须选择同一个活动默认路由对象。
- RouterOS 信任模型必须把未知 WAN 写成“不可判”，不能把对象证据缺失扩展成转发面或业务面正常。

### 实现决策

- WAN 与接口统一为 `online | offline/down | unknown` 三态；数组缺失使用 `available=false`，不再与“权威来源明确返回空数组”混为一谈。
- 资源值使用 `number | null`，并分别记录 `observed` 与 `complete`。完整度不足可以限制完整结论，但不能擦除已观测到的单项危险。
- 建立规范化默认路由选择结果：只从明确的默认路由候选中选择，优先活动且启用的对象，并使用确定性次序；派生状态保存 `selected`、`verified` 与 `candidates`。
- 移动、桌面与 RouterOS 证据模型全部消费该同一选择结果，禁止各自重新按 distance、首行或任意 active 路由拼接结论。
- `current | historical | unavailable` 同时吸收核心采集错误、辅助通道错误和失败端点；局部失败不能继续宣称“当前证据完整”。
- 条件资源仪表只渲染真实观测值；缺失值不得为了满足 DOM 或视觉布局而补零。

### 当前验证与边界

以下聚焦检查已经通过：

- `npm run check:mobile-native-model`
- `npm run check:types`
- `npm run check:overview`
- `npm run check:sections`
- `npm run check:runtime-schema`

这只证明 P0 证据合同的聚焦回归已闭合。当前工作树尚未形成新提交，尚未上传 GitHub，也尚未为最终精确 SHA 生成完整矩阵或 Linux / Windows / GHCR CL。typed metadata、稳定重复对象身份、筛选后 URL/详情一致性、领域化详情、手机视觉与平板任务架构仍未完成，公众发布继续禁止。

### 日志镜像说明

仓库内 `docs/panel-redesign-decision-log.md` 继续作为唯一来源，D 盘镜像文件 只做单向镜像。常规沙箱的可写根目录不包含 D 盘，所以普通写入会被文件系统策略拒绝；这不是目标受阻，也不是内容冲突。同步必须使用仅覆盖这一目标 Markdown 的受控写入，并在写后比较 SHA-256，绝不从 D 盘反向覆盖仓库。

## 第 53 步：让列表、排序、详情与 URL 消费同一份结构化事实

### 为什么不能继续从显示文字反推业务状态

第 52 步解决了概览层的未知、部分观测与默认路由真值，但领域工作区仍可能从已经本地化的单元格文字中判断异常、协议、流量和时间。这会产生三个问题：翻译或格式变化会改变业务行为；`100 Gbps` 与 `900 Mbps` 不能靠字符串可靠排序；日志正文里偶然出现 “error” 也不等于事件级别为错误。对象 ID 若依赖数组顺序，筛选、翻页和快照重排后，URL 还可能指向另一个对象。

### 实现决策

- `SectionTable` 新增与行并行的 `rowMeta`，统一保存状态、异常、运行/启用/活动三态、协议、流量、连接数、RFC 3339 时间、地址、距离、利用率、样本数、规则顺序和稳定身份原料。
- 搜索仍只匹配用户看得见的文字；业务筛选与排序只消费 typed metadata，不再解析翻译后的 DOM 文本。
- 列表行和事故深链共享同一个原始身份组合器。ECMP 路由把 distance、protocol 等路由语义纳入身份；完全相同的重复日志确定性折叠并记录重复数；语义不同但基础键相同的对象使用稳定签名后缀，不再使用依赖输入顺序的 `duplicate-N`。
- 把纯行构建与去重提取到 `mobileWorkspaceRows.ts`，而不是放宽 320 行维护性门禁。架构检查因此继续保护复杂度边界。
- 详情选择只允许解析到当前筛选、排序和分页结果中的对象。筛选移除已选对象时，详情、URL 的 `object` 参数和焦点状态同步收回；平板不再静默选中第一行。
- 领域页进一步收紧未知语义：缺失 WAN/接口数组显示“未取得”；缺失 active、disabled、PCC 标记显示“未确认/未记录”，不能伪装成非活动、启用或未识别。

以下聚焦检查通过：

- `npm run check:types`
- `npm run check:mobile-native-model`
- `npm run check:sections`
- `npm run check:runtime-schema`
- `npm run check:overview`
- 生产构建完成，架构门禁为 `mobile=210 / domain=408 / evidence=451 / minMobileText=12px`。
- 生产浏览器门禁为 47 项、21 个状态工件：实际 DOM 行顺序随业务排序改变；Back 关闭详情、Forward 恢复详情；快照重排后仍选中同一对象；筛选移除对象时详情与 URL 原子清除；200% 文本重排和 LAN 请求行为继续通过。

这些仍是**未提交工作树证据**。报告中出现旧 HEAD `19497d0` 只表示运行命令时 Git 提交尚未更新，不能把这些结果归属到该旧 SHA，更不能继承旧 SHA 的远端 CL。

### 视觉复核推翻的完成假设

重新查看 390×844 对象详情和 768×1024 平板工件后，确认当前通用 `<dl>` 仍是“字段展示壳”，不是领域化运维详情；手机详情下半屏大面积空白，平板也只是列表与同一字段表机械并排。这里不是缺少可信证据，而是接口计数器、父子关系、默认路由影响、日志上下文等已有数据尚未进入正确的信息架构。

因此下一步不是给通用字段表换颜色或补阴影，而是删除该通用详情策略，分别建立接口、路由、终端、日志、安全和 DNS 检查器；手机把常驻搜索/筛选/排序收进按需工具，尽早露出首个事故对象；平板持续保留扫描列表与领域详情的任务关系。

## 第 54 步：三路独立设计评审收敛为一套移动任务架构

### 评审方法

在不修改代码的前提下，对同一真实 390 对象详情截图、现有移动契约、`PRODUCT.md`、`DESIGN.md`、移动组件和 section 模型做三路独立评审：

1. 方向 A：紧凑巡检账本；
2. 方向 B：原生对象检查器；
3. 方向 C：网络 master-detail 控制台。

三路没有互相引用，但都指出同一组结构性问题：首个对象出现过晚、通用 `<dl>` 没有新增证据、768 只是机械分栏、平板隐藏 trailing state、常驻搜索/筛选/排序占用首屏，以及装饰图标、模糊阴影和重复“只读证据”不能替代真实任务关系。

### 综合取舍

不选择任何一张概念稿整套照搬，而是按任务采用三者各自最强的部分：

- **390 手机首页与领域列表采用方向 A**：证据边界、事实结论、最高风险对象、已验证路径按三秒扫视顺序出现；首个对象必须尽早进入首屏。搜索、筛选和排序改为按需展开的真实工具。
- **手机对象详情采用方向 B**：以“对象身份 → 证据边界 → 领域关键事实 → 依赖/影响 → 原始标志或更多证据”组织。接口、路由、终端、日志、安全、DNS 分别拥有自己的检查器，禁止再回到任意 columns 驱动的通用字段墙。
- **768–1023 平板采用方向 C**：稳定任务栏、可比较对象列表和持续证据工作区同时存在；事故时默认聚焦最高风险对象，正常时聚焦已验证默认路由与承载 WAN 的关系。右栏不得再显示“未选择对象”的大空态，也不得为了双栏隐藏对象状态。
- 状态变化必须真正替换布局：接口 Down 以影响链取代正常仪表；采集失败只显示采集边界和最近成功证据；资源满载以阈值、窗口、样本数和来源占据主位。颜色只能辅助，不能承担语义。
- 字段级关系允许部分可用：接口状态可以是当前，而成员关系可以是未采集。全局 evidence mode 不能把所有字段粗暴染成同一可信度。

### 明确删除清单

- 通用详情 `<dl>` 与平板空检查器；
- 手机整个账本外的大圆角容器；
- 首屏常驻搜索框、筛选排和排序排；
- 无真实对象、计数或目标的 Chevron 与关联入口；
- 重复的“当前只读快照/当前只读证据”页脚；
- 平板隐藏 `.mdw-row-state` 的规则；
- 普通 chrome 的 blur、软阴影、装饰性大图标和高频 `scale()` 按压动画。

## 第 55 步：以类型化领域证据替换通用详情壳，建立手机巡检与平板检查任务关系

### 为什么必须删除通用详情，而不是继续给它补字段

第 54 步已经确认，接口、路由、终端、日志、安全和 DNS 共用 `<dl>` 字段墙，会把不同运维任务压扁成同一种“键值查看器”。列表与详情因此反复展示相同文案，用户多点一次却没有获得关系、影响或原始证据。继续增加字段只会制造更长的规格表，不能形成产品信息架构。

本轮因此没有在旧详情上小修小补，而是删除 `DetailPane`、`.mdw-detail-fields` 和通用 `<dl>` 路径，新增类型化 `SectionRowEvidence` 联合类型，并让每个对象详情直接消费自己的领域证据。缺失值保持 `null / unavailable`，明确观测到的零继续是有效事实；任何界面都不得为了排版补零或从本地化文字反推业务状态。

### 六类领域检查器与证据边界

- **接口**：对象身份、运行/禁用状态、父子/VLAN/MAC/地址关系、收发速率与累计计数、丢包/错误质量、默认路由关联及其可验证边界。
- **路由**：默认/活动/禁用、路由表、距离、网关、静态/动态、协议族和原始备注；只允许明确的路由对象支撑默认出口结论。
- **终端**：地址与接口身份、DHCP/ARP 来源、租约和可达证据；无法关联时明确写未取得，禁止猜测设备关系。
- **日志**：严格 RFC 3339 时间、严重级别、主题与正文上下文；无时区原始值不再伪装成绝对时间。
- **安全**：告警与规则分型、链、动作、顺序、匹配条件和计数器，避免把规则存在误写成规则命中。
- **DNS**：规则、IPv6 ND 与 DHCPv6 分型，展示上游配置和 DoH 配置，但配置存在不等于解析成功。

资源和连接也获得了范围明确的检查器；只有尚未完成领域模型的低频对象保留带明确标签的降级回退，不能再被称为完整运维模块。

### 手机与平板任务架构

- 390 手机列表改为扁平巡检账本：证据边界和首个风险对象先出现，搜索、筛选、排序收进真实的按需“筛选”工具，不再常驻占用首屏。
- 行项目使用紧凑状态轨和对象事实，不再重复青色图标方块、装饰 Chevron、模糊阴影或缩放动画。
- 手机详情成为真实领域目的地，并提供与对象类型一致的返回语义；Back 关闭详情，Forward 能恢复同一对象。
- 768 平板持续保留可比较对象列表与领域检查器。未显式选择时，只在界面内预览最高风险对象、活动默认路由或第一可见对象，不写入 URL；用户显式选择后才进入真实历史状态。
- 过滤掉已选对象时，列表、详情和 URL 原子收回；平板不再因为进入详情而隐藏扫描列表，也不再隐藏行状态。
- 普通表面统一为不透明、低圆角、无毛玻璃的运维层级；触控目标至少 44px，移动正文最小 12px。颜色只辅助状态，不能替代证据语义。

### 本轮自动验证与不能夸大的边界

当前未提交工作树已经通过：

- `npm run check:types`
- `npm run check:sections`
- `npm run check:overview`
- 生产构建
- 生产浏览器门禁 `48 checks / 21 snapshots`

浏览器门禁实际验证了按需工具、首对象位置、真实排序变化、接口领域详情、证据边界、关系区、Back/Forward、平板列表持续可见、44px 触控、对比度和既有 200% 文本重排路径。门禁曾真实发现并推动修复 42px 触控、3.66 对比度、首对象 232px、平板详情误隐藏列表和返回文案不匹配。

这些仍然只是**当前脏工作树的工程证据**，不是 `19497d0` 的精确 SHA 证据，也不能代替视觉签收。六类检查器仍需补齐逐领域运行时流程；390 与 768/844 截图还必须逐张人工复核；1024 能力边界、后端最小拆分、内容哈希与压缩缓存、完整矩阵及 readiness 仍未闭合。因此本轮没有提交、没有上传 GitHub，公众发布继续禁止。

### 日志镜像和心得

仓库内本文件仍是唯一来源。D 盘镜像文件 只允许从仓库单向覆盖，并在写后比较字节数和 SHA-256；D 盘不在本轮常规沙箱写入白名单中只是执行权限边界，不是产品目标受阻。

心得：领域化不是把标题从“详情”改成“接口详情”，而是让每一次进入都增加新的判断。手机负责迅速找到对象，详情负责解释关系与影响，平板负责保持比较上下文；三者若展示同一组字段，再精致的颜色与圆角也只是重复。

## 第 56 步：让领域证据、截图复核与响应式边界共同否决“自动通过即完成”

### 为什么自动门禁通过后仍要继续改

第 55 步建立了领域化检查器的结构，但当时只有接口流程获得较深的运行时验证，手机和平板的构图也还没有逐张收敛。运维产品不能把组件存在、DOM 数量或矩阵绿色当作视觉和信息架构已经成立；真正的完成条件必须同时包含：事实语义正确、进入详情后获得新证据、常见视窗不裁切，以及截图中对象比较与任务重心确实清楚。

本轮继续采用产品公司 loop，并把 Emil Kowalski 的设计工程原则融入本项目适配层：频繁动作必须直接、动效必须解释状态变化、没有行为的控件不得制造交互暗示、视觉层级服务于任务而不是装饰。这里没有照搬某个作品的皮肤，也没有重新引入假毛玻璃、假 sheet、装饰拓扑或无功能手柄。

### 领域证据和检查器的进一步闭合

- 接口、路由、终端、日志、安全、DNS 六类检查器继续保持独立信息结构；连接和资源也使用范围明确的检查器，不再回退为任意字段墙。
- 路由详情新增“关联接口”证据，只接受出接口或网关的明确关联，不能因为数组第一项或名称相似就宣称默认路径成立。
- 终端详情把 DHCP 与 ARP 证据串联；DHCP 租约和 ARP 对象都能获得对应上下文，ARP 告警不能再冒充终端对象。

## 第 57 步：完成静态资产发布契约，并让真实截图继续否决错误的“产品完成”叙述

### 为什么这一轮同时处理静态发布与工作区设计

手机与平板界面即使在本地看起来成立，只要每次重载仍重新下载未压缩的大型 JS/CSS，公众产品的移动体验就没有闭环；反过来，缓存和 CI 全绿也不能证明信息架构正确。因此本轮把两条证据链并行推进：静态资产必须具备可验证的内容身份和传输契约，手机、平板与桌面工作区则继续接受真实截图和领域任务的否决。

这两条线不能互相冒充。内容哈希证明的是“浏览器拿到哪一份代码”，截图证明的是“用户看到什么任务重心”，领域模型证明的是“界面是否有资格说这句话”。任何一条未闭合，都不能写成公众发布完成。

### 内容寻址、压缩与缓存契约

- 构建流程在保留兼容入口的同时生成带 12 位内容摘要的 JS/CSS 文件、`manifest.json`、gzip 与 Brotli 旁车，并在构建阶段反向解压校验，避免只生成文件名却没有证明内容可还原。
- `public/index.html` 改为引用内容哈希入口；无意义的 HTML cache-control meta 被删除，缓存语义由 HTTP 响应头统一负责。
- 后端新增独立静态资产解析模块：只有内容哈希资产可获得一年期 `immutable`；未哈希静态入口使用 `no-cache`；API JSON、403 和 404 继续 `no-store`。
- 静态响应支持 `br`/`gzip` 协商、`Vary: Accept-Encoding`、ETag 和条件请求 304；安全集成检查通过真实 HTTP 请求验证这些行为，而不是只搜索源码字符串。
- Dockerfile、Linux CI、Windows 打包和 readiness 门禁已接入清单与哈希入口检查，并阻止构建后生成物与仓库内容漂移。

当前工作树中的静态资产、后端安全、后端发布阻断、采集回归、类型、模块、运行时 schema、移动模型和总览聚焦检查均曾通过。Docker Compose 配置解析通过；本机 Docker 构建检查因 Docker Desktop Linux engine 未运行而无法形成镜像证据。因此只能说源码和发布契约已经接通，不能说容器构建已被本机证明，更不能用它代替最终 GHCR CL。

### 截图发现的平板预览错误

自动门禁一度允许 768px 平板默认预览 `bridge-lan`，但截图显示：明明存在已验证的默认路由与 WAN 关系，右侧检查器却先展示普通 LAN 对象。这个选择在类型上合法，在产品上错误，因为平板首要任务是让默认出口或最高风险对象立即可检视。

平板默认预览优先级因此改为：最高风险对象，其次是明确承载活动默认路由且运行中的接口，再其次是活动默认路由对象，最后才是第一条可见对象。用户未显式选择时仍只做界面预览，不污染 URL 或浏览器历史；显式选择后才建立可回退、可前进的真实对象状态。新的运行时检查会明确断言默认 WAN 预览，避免再次退化为“第一行看起来也能用”。

### 桌面端不再依赖通用表格壳

1366px 截图暴露出桌面树仍是稀疏通用表格，和已经领域化的手机/平板不是同一套任务语法。本轮没有复用手机组件去伪造响应式，而是建立独立桌面渲染树：对象列表负责比较与定位，右侧领域检查器负责解释关系、影响和原始证据。

桌面工作区现在具备真实搜索、类型化筛选、类型化排序、分页、风险或默认路由载体预览、显式对象选择、URL 身份以及 Back/Forward。接口、路由、终端、日志、安全、DNS、资源和连接进入相应领域检查器；仅尚未完成领域建模的低频对象保留明确标注的降级回退。旧的通用 `DataTable` 已退出该工作区，历史状态键也由手机专用命名改为表面中性的对象命名。

生产浏览器门禁曾达到 **66 项、30 个状态工件**，覆盖平板 WAN 预览、桌面接口工作区、桌面对象 Back/Forward，以及路由、连接、DNS4、DNS6、安全、终端、日志和资源八类桌面目的地。截图复核确认桌面已有真实列表—检查器关系；这仍是当前未提交工作树的运行时证据，不是候选 SHA 的发布证据。

### 本轮仍被截图否决的问题

最新历史快照截图同时出现“历史证据”和“采集通道部分可用 / 可用通道 2/2”。后两句会把很久以前的记录读成当前状态，语义与证据鲜度直接冲突。正确做法是把历史模式写成“当前采集状态不可确认”或“上次采集记录”，只有当前证据才可以声称通道可用或部分可用。这个问题仍待模型、聚焦测试与截图共同闭合，不能因为静态资产和 66 项运行时检查曾通过就放行。

### 后端、发布与日志镜像的真实边界

## 第 59 步：把 HTTP 分发、领域快照和采集生命周期从后端单体中真正拆出

### 为什么选择这三个边界

目标评审指出 `app.py` 同时承担 Collector、HTTP 路由、静态服务、安全、配置和领域转换。这里没有换 Web 框架，也没有一次性重写采集器，而是按照建议只移动三个可以独立验证的责任：请求分发、领域 snapshot 构建、Collector 生命周期。URL、状态码、JSON 字段、会话/CSRF、缓存头、采样周期、锁和线程 daemon 行为必须保持不变。

### HTTP dispatcher

## 第 60 步：首个候选 SHA 被真实预部署启动否决，并补上缺失的 HTTP 路由回归

## 第 61 步：76 格矩阵揭露验收器仍在检查已经退役的桌面表格

### 先承认失败，不让 28 格结果越权

接口页在当前证据模式下还必须有真实对象行、`interface` 类型检查器和至少四个领域证据区块；证据不可用时只能由明确空状态通过。这样修的是“门禁与真实产品契约错位”，不是降低产品标准，也没有用 `|| true`、视窗白名单或跳过桌面的方式制造绿色。

## 第 65 步：分段矩阵的“聚合未完成”不能冒充产品失败，更不能把整个目标标记受阻

实际运行 266 格路由状态矩阵时，单个事故场景的 38 个浏览器格子和 38 个矩阵格子已经全部通过，`matrix.failed=0`，但旧运行器仍会附加一项“统一发布场景矩阵尚未覆盖全部必测场景”的合成失败。这项结果描述的是跨批次聚合尚未完成，不是当前批次产品失败。原检查点合并器要求每个输入报告的 `failures` 必须为空，因此会把一个可恢复、已通过的分段检查点错误丢弃。

本轮修订 `merge_matrix_reports.py`，但没有宽松忽略失败。它只接受唯一一种精确形状的检查点状态：

- 失败名称必须是统一发布场景矩阵覆盖检查，且 `pass=false`；
- 报告 commit 必须与候选 SHA 完全一致；
- 当前请求已完整运行，但当前批次不足以覆盖全部发布必测格；
- 聚合和发布矩阵仍为未完成；
- 当前覆盖场景与当前通过场景完全一致，并与矩阵自己的覆盖/通过场景一致；
- `matrix.failed=0`，所有矩阵格和浏览器格仍必须逐项通过；
- 任何额外失败、意外失败、重复格、候选不一致或缺失格继续硬失败。

聚焦验证结果：

- Python 语法编译通过；
- 旧完整 266 格报告仍可严格合并；
- “基础 76 格 + 全离线 38 格”能被识别为有效检查点，最终仍因缺少其余 152 格而正确拒绝生成完整报告；
- 人工注入的意外失败被拒绝；
- 重复输入报告被拒绝。

这次修复同时纠正 Loop 的状态语义：远端公开披露门禁、Docker 门禁或某个分段矩阵未完成，只能标记对应阶段为 `pending` 或 `gate failed`，不能把仍有大量本地工作可推进的整个目标标成 `blocked`。只有同一阻断连续出现至少三轮且已经没有任何安全进展路径时，才允许目标级阻断。

心得：可恢复流程必须区分“这个批次失败了”和“全局事务尚未结束”。如果两者共用一个布尔值，Loop 不是更严格，而是在制造误报、诱导停工。严格门禁应该拒绝真实失败，同时保留可验证、可继续的成功检查点。
