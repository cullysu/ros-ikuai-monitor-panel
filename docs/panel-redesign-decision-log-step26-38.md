# 面板重做决策日志续篇（第 26–38 步）

## 第 26 步：目标从未受阻，继续拆除不稳定桌面门禁

### 状态澄清

本轮开始时重新读取持久目标，状态为 `active`，从未调用“blocked”。界面出现“受阻”感，是因为旧桌面运行时检查在手写 CDP WebSocket 上超时，并不是整个目标停止。正确处理方式是把它当作一个局部失败继续诊断；只要仍有可做的安全工作，就不能停住，也不能把一次工具失败写成目标受阻。

### 旧 CDP 的根因与决策

旧 `check-resource-trend-balance.js` 自己分配调试端口、启动 Edge、轮询 JSON 端点、建立 WebSocket，再由三个包装器最多重试四次。它既可能留下浏览器锁，也会把第一次真实失败隐藏在“后来重试通过”之后。决定保留验收语义，但删除手写传输层：改用 Playwright `chromium.launch`、独立 context、页面异常收集、全页工件、120 秒全局超时和显式 context/browser/server 回收；三个包装器改为单次运行，失败立即暴露。

迁移后第一次并非通过，而是暴露了真实产品崩溃：当前 WAN 速率存在，但 history 没有带时间样本时，`DesktopWanEvidence` 仍读取 `last.down`。这说明“浏览器连通问题”修好以后，门禁终于看到了真正的空样本边界。产品改为显示“时间序列正在积累”，保留当前上下行读数，不画伪趋势；测试夹具使用 RFC 3339 `Z` 时间戳，并新增专门的 `desktopTrafficAccumulating` 用例，防止以后再次读空数组。

### 结果与心得

桌面正常趋势、趋势积累、无快照、全 WAN 离线和资源满载均在第一次 Playwright 运行通过；无 7–9px 文本、无裁切、无横向溢出、首屏状态和工作区均满足当前共享桌面契约。心得：重试不是稳定性，重试会掩盖稳定性；应先让单次失败可复现，再修传输层和产品边界。旧脚本约两千多行失效 DOM 规则被当前共享检查器替换，测试不再为已删除的页面结构守灵。

## 第 27 步：区分产品失败与本机 Python 启动失败

56 格手机矩阵第一次重跑在任何浏览器格子开始前就出现 `fetch failed`。报告的 serverExit 明确显示本机 `python` 命中了 uv trampoline，受当前沙箱限制无法创建 Python 子进程；显式指定真实解释器后又暴露缺少 `requests`，说明后端仍未启动。这不是手机产品失败，也不能靠重试或改门禁冒充通过。

决定让手机矩阵启动器优先解析真实 Python：显式 `CODEX_PYTHON_PATH/PYTHON`、项目 venv、用户 Codex bundled runtime，最后才回退系统命令；同时 `local-predeploy-check.js` 在存在 `_acceptance/python-deps` 时把它合并进 `PYTHONPATH`。这样本地不再依赖偶然 PATH，CI 仍使用 setup-python 的标准环境。修复后同一命令完成 7 场景 × 8 视口，56/56 与 56 张截图全部通过。

心得：门禁报告必须先回答“被测产品是否真的启动”。后端没启动时，矩阵覆盖为零是环境证据，不是视觉或业务结论；但环境问题也必须修到命令可复现，不能让操作者每次手工配变量。

## 第 28 步：重新生成完整工作树证据，并单独做人工截图复核

当前未提交工作树重新生成：手机概览 56/56；公众 overview 28/28；19 路由 × 4 视口 76/76；19 路由 × 7 场景 × 手机/桌面 266/266；生产运行时 36 项与 13 个状态工件；readiness、TypeScript、Schema、section 模型、概览架构、后端安全、生产时间阻断、采集回归和 LAN 默认均通过。

人工复核没有发现旧手机壳、假 sheet、任意路由兜底、缺失速率写成零或事故仅换颜色的回归。但这仍是实现者内部复核，不冒充用户视觉签收。当前不写“产品审美已通过”，更不写“可以公众发布”。

因此 Linux CL 新增：编译并执行 `check-backend-release-blockers.py`；执行 `check-release-blockers.js`；运行 `npm run build` 后对两份 framework 资产做 `git diff --exit-code`；运行桌面正常趋势、趋势积累、无快照和事故层级全部门禁。发布阻断器反向检查 CI 必须包含这些命令，防止以后静默删掉。Windows preflight 已按当前 `<main id="app">` 验证并拒绝退休 legacy shell，不再要求旧 `data-app-shell`。

### 当前发布状态与下一步

### 本轮心得

1. 目标状态和局部工具失败必须分开；只要仍能推进，就继续解决，不标记 blocked。
2. 事实语义、交互、视觉和发布链是四本账；任何一本不能被另一本文字替代。
3. 真实“积累中”比空数组崩溃或伪造趋势都更专业。
4. 运行矩阵必须显式记录解释器、依赖、视口、场景和提交，避免环境偶然性。
5. CI 绿色只对它实际执行的检查负责，因此 CL 配置本身也必须被发布阻断器审计。
6. 当前结论仍是：工程工作树通过，产品等待用户视觉复核，公众发布关闭。


## 第 30 步：时间契约不能只修测试，还要拒绝“看起来能解析”的错误日期

复核生产时间链路时，后端已经统一输出带 `Z` 的 RFC 3339，但前端的严格检查仍把最终判断交给 `Date.parse`。浏览器会把 `2026-02-30T10:00:00Z` 自动滚到三月，这种“能解析”不等于协议合法。决定在 `timeContract.ts` 先验证月份天数、24 小时时钟、分秒和时区偏移范围，再允许解析；同时在运行时 Schema 测试中加入不存在日期，阻止以后又退回猜测式时间处理。

心得：时间正确性有三层——格式带时区、日历值真实、前后端使用同一契约。只修快照夹具或只看 `Date.parse` 都不够。

## 第 31 步：空壳快照不能被判成可运维证据

发现一个结构完整但业务为空的响应——`meta: {}`、`overview: {}`、空 interfaces/wan——仍可能进入 operational。原因是旧判断把“有 overview 对象”误当作“有 overview 观测”。决定要求当前 envelope、meta/overview 结构、预期集合和至少一项有意义观测同时成立；明确观测到的数值零仍然保留为有效证据，缺失值不会被伪装成零。

同时把生产运行时浏览器门禁的硬 `process.exit` 看门狗改成 `Promise.race` 与幂等清理：超时也必须关闭 context、browser 和 mock server。发布阻断器反向检查这一生命周期，禁止重新引入手写 WebSocket/CDP。

心得：Schema 的“对象存在”和运维的“证据存在”不是一回事；超时退出和可复现清理也不是一回事。

## 第 32 步：矩阵通过后仍要对照生产字段，不能只相信夹具

逐项比对后端真实输出和前端 section 模型，发现连接后端使用 `localIp/remoteIp`，前端却读 `srcAddress/dstAddress`；终端的 `reachable` 被当成离线；日志重复 topic 而隐藏 message；REST 已采到 `dhcp_clients`，但 `build_dhcp()` 丢弃了它。这些问题此前矩阵未发现，因为验收夹具也沿用了错误字段名。

决定同步修正生产映射、保留 DHCP 客户端证据，并重写安全夹具，使连接、DHCP、DNS、路由、分流和日志结构与生产契约一致。新增 section 模型和 collector 回归，确保真实地址、消息、终端状态和 DHCP 客户端不再被吞掉。

心得：Mock 与产品使用同一个错误词汇时，76/76 也只能证明错误自洽。高价值验收必须以生产数据契约为基准，而不是以前端当前实现反向造夹具。

## 第 33 步：把“19 个 URL”升级为“19 个有真实证据的路由”

旧路由矩阵主要验证标题、容器和 URL，无法发现连接页没有地址、日志页没有消息、DNS 页字段为空。决定在浏览器检查器中为每个 single 路由规定一组来自生产夹具的语义证据：接口名、默认路由、MAC、CPU 样本、协议连接数、本地/远端地址、DNS 规则、日志 message 等。报告保存 `operationalTextExcerpt`，失败时可以直接看到产品实际展示了什么。

首次 19 路由语义烟测全部通过，但同时暴露手机 `more` 页仍显示路由表：这正是新门禁应当发现的产品问题，而不是应被放宽的检查。

## 第 34 步：更多工具必须是目录，不能是路由表兜底

根因是手机分支先把所有路由交给 `MobileDomainWorkspace`，`more` 又被 `buildSectionModel` 的路由模型兜底；桌面专用 `MorePage` 永远到不了手机。决定在手机树中建立独立 `MobileMoreDirectory`：10 个真实入口分成“路径与性能 / 审计与服务”，每项使用对象图标、正式标题和真实用途说明；平板使用两列等高任务目录，而不是空白检查器。额外工具不再错误点亮底部“网络”任务。

验收对手机 `more` 特判为目录契约：必须恰好有 10 个真实入口，必须出现资源、DNS、安全证据，且禁止出现旧兜底的“路由记录”。重新构建后，19/19 手机路由语义烟测通过；顶层 `pass` 仍因该烟测不是完整发布矩阵而保持 false，这是正确行为。

### 当前状态

目标仍为 `active`，没有标记 blocked。当前阶段是 **Verify**：先完成静态、运行时、桌面与完整矩阵复验，再做精确 SHA 提交和发布链验证。GitHub 尚未上传，本轮也没有复用旧 SHA 的 CL 结果。


## 第 35 步：完整矩阵不能靠反复启动浏览器碰运气

56 格矩阵第一次在第 43 个格子启动 Edge 时中断，前后产品格子均通过。根因不是资源场景，而是 `local-predeploy-check.js` 在每个视口循环里重新启动一个浏览器进程；完整矩阵因此累计启动 56 次 Edge，把进程抖动误报成产品失败。

决定把浏览器生命周期提升到矩阵级：一次矩阵只启动一个 Playwright browser，每格建立独立 context，格子结束显式关闭 context，最外层 finally 关闭 browser。发布阻断器要求源码只出现一次 `launchBrowser`，并检查 context 和 browser 的清理路径。修复后同一 56 格命令首次完整通过，没有依赖重试。

心得：场景隔离应使用 browser context，不应通过反复创建操作系统进程实现。稳定门禁的标准是单次可复现、失败归因准确、清理可证明。

## 第 36 步：语义门禁必须允许表面差异，但不能允许证据消失

完整 76 路由检查暴露两类问题。第一类是真产品问题：手机安全列表把规则顺序“未记录”放在主标题，真正的 `allow established` 被埋到次级字段。决定让防火墙规则以 comment 作为对象身份，以 chain/action 为上下文；安全事件则以 message 为对象身份。第二类是合法的表面差异：桌面显示 `TCP / 3`，手机显示 `3 个连接`；桌面工具目录使用短标题，手机使用完整标题。

因此门禁不再强迫两端逐字相同，而是用等价正则验证同一业务事实；同时继续要求每个路由出现生产字段对应的对象证据。聚焦 9 格修复烟测与后续 76/76 均通过。

心得：跨表面一致性是事实、层级和任务一致，不是复制同一句 DOM 文本；但“措辞不同”也不能成为空字段或错误对象身份的借口。

## 第 37 步：矩阵通过后，截图仍然可以否决当前布局

人工查看 390 与 768 截图时发现，`no-snapshot`、`collection-down` 虽然事实正确，仍在下半屏留下明显空洞；768 平板虽然两栏存在，仍只是现有模块并排。决定不靠重复指标填空，而是增加真实、只读、可导航的任务入口：采集异常进入诊断、日志和工具目录；WAN、接口、资源和路由风险分别进入所属对象与审计工作区。手机按“异常对象 → 证据台账 → 处置入口”排序，先看证据再行动。

平板把来源台账在采集事故中移到对象列表一侧，另一侧保留所选对象的字段证据与处置入口；竖屏平板两栏同高，并让台账或入口按剩余空间伸展，形成持续工作区而不是短卡片。新增浏览器语义检查要求该入口只在采集事故手机或所有平板出现、恰好三条且全部指向真实路由；平板竖屏要求主从栏同高。

200% 文字门禁同时覆盖新增入口的标题与说明。当前生产浏览器门禁 36 项、13 张工件通过，其中真实文本由 20px 放大到 40px、无横向丢失、触控目标不低于 44px。心得：自动化负责防回归，截图负责发现自动化没有提问的问题；两者任何一方都不能替代另一方。


## 第 38 步：连接页默认任务必须是连接，而不是展示所有传输参数

复核目标清单时确认，连接页仍把 SSH 端口、REST 协议、REST 端口和证书校验与地址、用户名、密码放在同一层级。虽然字段都真实，默认任务却被高级参数淹没。决定将主表单收敛为地址、用户名、密码；传输参数进入原生 `details` 渐进披露。摘要始终显示 `HTTPS 443 · SSH 22 · 证书校验`，若选择 HTTP 或关闭证书校验则明确显示“风险模式”，因此折叠不等于隐藏安全边界。

生产浏览器门禁新增两项事实：首次进入高级区必须关闭且不占布局；点击摘要后 SSH、REST 端口和协议控件必须真实可见。连接页截图显示提交按钮从首屏底部上移到约 666px，390×844 下无需先滚过四项高级设置。运行时门禁现为 37 项、13 张工件。

同时重新统计活动前端样式：12 个 CSS 文件中 `!important` 为 0，最小固定字号为 12px；`OverviewPanel.tsx` 为 53 行。旧架构门禁仍允许构建 CSS 出现 650 个 `!important`，与当前重构结果矛盾，因此改成零容忍。心得：债务已经清零时，门禁还保留历史宽限，就是在为回归预留合法入口。


## 第 39 步：发布必须证明远端树与本地验收树相同

本地完整门禁通过后，不能因为普通 `git fetch` 的 Schannel 凭据错误就把目标标记 blocked，也不能退回普通 `git push`。决定继续使用 GitHub Git Data API：逐个创建 83 个新增或修改 blob，显式提交 10 个删除，以父树构建新树。第一次大文件上传暴露 `shell_command` 输出截断，`app.py` 的 blob SHA 不一致；因为分支尚未移动，这只是不可达对象，不构成发布污染。随后改为 12,000 字节分块读取，每块校验长度，每个 blob 校验 Git SHA，最终远端树 `f846723428c87edfc5ad8173879adaf8742d726d` 与本地树完全一致。

移动 `main` 前再次证明远端仍等于预期父提交，并使用 `force:false` 快进。远端提交 SHA 因 GitHub 生成的提交元数据与本地提交不同，所以本地矩阵证明的是同一棵树，远端 CL 则必须重新证明远端精确 SHA。心得：上传是否安全取决于父提交竞争检查和树身份，不取决于命令是否叫 push；CL 证据必须绑定最终远端提交，不能从树相同推断工作流已通过。

## 第 40 步：第一次远端失败是焦点时序竞态，不是停止理由

首个远端 SHA 的 Windows packaging 与 GHCR 成功，Linux 在“浏览器 Back 关闭详情并恢复焦点”失败。日志显示 URL 与对象都正确，唯一失败值是 `backFocus=false`。产品代码在详情关闭后先提交 DOM，再用 `requestAnimationFrame` 恢复列表按钮焦点；Linux runner 恰好在下一帧之前完成断言。本地偶然通过不能证明状态机确定。

决定不延长测试等待，也不增加轮询，而是把详情标题与返回列表按钮的焦点恢复放入 `useLayoutEffect`，在 React DOM 提交阶段同步完成。重新构建公开 bundle 后，37 项浏览器检查通过。心得：可访问焦点是可观察产品状态，不能作为“下一帧大概会发生”的视觉副作用。

## 第 41 步：修复必须进入发布 bundle，而不只是源文件

第一次本地复验时，源文件已修改，但浏览器门禁读取的是已提交的 `public/assets/framework/panel-framework.js`。因此那次通过仍可能是在验证旧实现。决定先运行生产构建，再验证构建产物无未提交漂移，随后重新跑浏览器门禁；只有源码、bundle 和运行时检查同时指向同一实现才提交。

心得：源代码测试、构建确定性和静态公开资产是三个不同证据。任何一个没有绑定当前提交，都不能写成“修复已验证”。
